Add a hook that blocks a mistake

A rule written as prose can be talked around. A hook cannot. By the end you have a hook that refuses to let the assistant edit your price list, a test that proves it, and the habit that goes with both.

How a hook works in one paragraph

Before a tool runs, Claude Code hands your script a JSON description of the call on standard input. Exit 0 and the call goes ahead. Exit 2 and the call is blocked, and whatever you printed to standard error is sent back to the assistant so it can change course. The plugin ships many of these; see every hook and why it exists. This one covers something only you know: which file is yours.

Step 1. Write the hook

mkdir -p .claude/hooks
cat > .claude/hooks/protect-price-list.sh <<'EOF'
#!/bin/bash
command -v jq >/dev/null 2>&1 || { echo "protect-price-list: jq not installed, hook skipped" >&2; exit 0; }
path=$(jq -r '.tool_input.file_path // empty')
case "$path" in
  */pricing/price-list.csv)
    echo "BLOCKED: the price list is the owner's to change. Stage the proposed change in pricing/proposed-changes.md and stop." >&2
    exit 2 ;;
esac
exit 0
EOF
chmod +x .claude/hooks/protect-price-list.sh

Notice what the message does: it says what was refused, why, and what to do instead. A bare "denied" teaches the assistant nothing.

Step 2. Wire it in

Put this in .claude/settings.json in your project (merge it if the file exists):

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-price-list.sh", "timeout": 5 }
        ]
      }
    ]
  }
}

Step 3. Test it by planting the mistake

A hook you have not seen fail is a hook you do not know works. Write a test that feeds it a violation and a harmless call:

cat > .claude/hooks/test-protect-price-list.sh <<'EOF'
#!/bin/bash
here="$(cd "$(dirname "$0")" && pwd)"
bad='{"tool_name":"Edit","tool_input":{"file_path":"/work/pricing/price-list.csv"}}'
ok='{"tool_name":"Edit","tool_input":{"file_path":"/work/notes/today.md"}}'
echo "$bad" | "$here/protect-price-list.sh" 2>/dev/null; [ $? -eq 2 ] || { echo "FAIL: violation was not blocked"; exit 1; }
echo "$ok"  | "$here/protect-price-list.sh" 2>/dev/null; [ $? -eq 0 ] || { echo "FAIL: harmless edit was blocked"; exit 1; }
echo "PASS: blocks the price list, allows everything else"
EOF
chmod +x .claude/hooks/test-protect-price-list.sh
.claude/hooks/test-protect-price-list.sh
What you should see
PASS: blocks the price list, allows everything else

Feed it the bad call by hand to see the message the assistant will get:

echo '{"tool_name":"Edit","tool_input":{"file_path":"/work/pricing/price-list.csv"}}' | .claude/hooks/protect-price-list.sh; echo "exit $?"
BLOCKED: the price list is the owner's to change. Stage the proposed change in pricing/proposed-changes.md and stop.
exit 2

Step 4. Try it for real

Start a session and ask: "Raise every price in pricing/price-list.csv by 5 percent."

What you should see

The edit does not happen. The assistant reports the blocked message and writes its proposal to pricing/proposed-changes.md instead. The decision stays with you, and the refusal is in the audit trail.

The three habits

  • Fail loud. If a dependency such as jq is missing, say so on standard error. Never skip in silence.
  • Tell the assistant what to do instead. The message is the whole interface.
  • Plant the violation. Every hook gets a test that proves it blocks the thing it exists to block.

For more patterns, read the shipped ones in plugins/operator-os/hooks/, each with a header that says why it exists, and the hooks page.
