Tutorial 3 of 4 · Fifteen minutes

Run the builder and reviewer loop

The seat that builds never grades its own work. By the end you have run one real change through a builder and a read-only reviewer, and you know how the loop ends.

Before you start

Use a real task in a project that has a test or a build command: a validation rule, a small report script, a copy fix. Start from a clean tree so the change is easy to undo:

git status
What you should see

nothing to commit, working tree clean. If it is not clean, commit your own work first, by explicit file names, so the loop's change stands alone.

Step 1. Ask the builder

State the outcome, the file, and how you will know it works.

Use the implementer agent to add a check to src/signup.js that rejects an empty
phone number with a clear message. Run the tests when done and report what changed.
What you should see

The implementer reads the file, edits it, runs your tests, and reports a short list: files changed, tests run, result. It runs on a mid-tier model at medium effort by design: scoped edits do not need deep thinking.

Step 2. Ask a different seat to check it

Use the reviewer agent to review the diff from git diff. Rank findings by severity,
with file and line and a one-sentence fix for each. End with one verdict: Pass,
Pass with conditions, or Block.
What you should see

Findings ranked worst first, each as file:line, then one sentence. No preamble and no restating the diff. If you open plugins/operator-os/agents/reviewer.md you will see why it cannot quietly fix things: Write and Edit are listed under disallowedTools. It runs at the highest effort because checking is where the strong model is spent.

Step 3. Read the verdict

A review ends in one of three words.

VerdictWhat happens next
PassMerge it.
Pass with conditionsProceed once the named conditions are closed.
BlockIt goes back to the builder with the failing items named.

Step 4. Send defects back down

Use the implementer agent to fix only these findings: 1 and 2. Do not change anything else.
Then run the tests again.

Then ask the reviewer again. Each pass is a round.

What you should see

The second review has fewer findings, and none of the ones you fixed. If the reviewer finds new problems in code you did not touch, that is the loop working: a fresh pair of eyes.

Step 5. Know when to stop

The loop has a stopping rule, not a clean-round target. Three rounds, then halt. If findings are still open after round three, stop, and read the matrix of what passed and what did not. A halt is a valid ending. Widening the tolerance, dropping a check or calling it close enough is not.

Why this shape

Reading back what you just wrote shares every blind spot of the writer. A reviewer that cannot edit has to send the work back, which is what makes the check real. See the review loop for the three-level accuracy hierarchy used when the output is a number someone will act on.
